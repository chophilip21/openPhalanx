# oppx permissions: what runs without asking, saved and session rules, the question

Part of the developer notes; the index is in `CLAUDE.md`.

* **Permissions** (`oppx_chat/permissions.py`, no UI code, modelled on Claude Code; `scripts/test_permissions.py`, 11 tests):
  * **Never asked:** a command whose every part (split on `&&`, `||`, `;`, `|`) only reads, inside the project: `git status/log/diff/show/blame/ls-files/grep`, `git branch`/`tag`/`remote`/`stash list`/`reflog`/`config --get` in their listing forms, `ls`, `cat`, `rg`, `grep`, `head`, `wc`, `find`, `cd` … Not when an argument points outside the project (`/etc/passwd`, `~/.ssh`, `$HOME`, `../other`; a pattern like `/api/v1` is not a path), nor with an argument that makes it write or run something (`find -delete/-exec`, `sort -o`, `tree -o`, `rg --pre`, `git --output`, `git -C`/`-c`, `uniq in out`), nor behind an environment assignment or a wrapper.
  * **Asked once:** **y** (this time), **N**, **a** (always), or any other text, which declines and is passed to the model as what to do instead. **a** saves an allow rule for the project in `~/.config/oppx/permissions.json` (`OPPX_PERMISSIONS`); a rule names what is run (`cargo test`, `npm run`, `git commit`, `python -m pytest`, `./scripts/x.sh` with its path, `cargo --version` as itself; never a bare interpreter, and a tool's name alone covers only the bare call, with `git *` by hand for all of it) and is matched word by word after stripping assignments and wrappers (`env`, `timeout 60`, `nice`), so `timeout 60 cargo test` is covered and `cargo testx` or `git -C x push` are not. Connector (MCP) tools: the same, by tool name.
  * **Asked every time, never remembered:** `sudo`, `su`, `rm`, `dd`, `mkfs*`, `shutdown`, `reboot`, `chmod`, `chown`, `truncate`, `shred`, `git push`, `git reset`, `git clean`; whatever runs text as code (`bash`/`sh -c`, `eval`, `xargs`, `ssh`, `python -c`, `node -e`); and anything that can't be taken apart safely (command substitution, output redirected to a file, background jobs, input redirection, an unclosed quote). `2>/dev/null`, `>/dev/null` and `2>&1` are fine. A rule for one of these written into the file by hand is ignored.
  * **For this session** (`s`; `Permissions.offer_session`, never written to disk): offered when a line can't get a saved rule only because a part is an interpreter given its code inline (`python3 -c`, `node -e`). It allows that interpreter's one-liners, and the line's other parts, until the chat ends. On such a line `a` saves what a rule can name (`curl`) and allows the inline code for the session. Not offered for the rest of the never-remembered list (`sudo`, `rm`, `git push`, a shell running text, anything that can't be taken apart); deny rules and plan mode still refuse. Why: asked to sort an API's results, Qwen3.6 read the JSON with six `curl … | python3 -c '…'` variants and the user was asked about every one, with `curl` already allowed. The `run` line of the system prompt now also says which commands run without a question and to read JSON with `jq` or `python3 -m json.tool`.
  * **The question** (`OppxIO.ask_options`; commands, connector tools, the browser): the answers are listed one per line, always in the same order (yes, always, session, no, free text), each key in its own colour (green yes, teal for the lasting ones, red no), under a bold yellow heading. They used to sit in one grey parenthesis after "Allow?" and were easy to miss. Seen in a pty; not yet in a live chat.
  * **A command that just failed isn't run again unchanged** (`failed_runs`): the same line after a non-zero exit, with no edit and no other command that worked in between, is a repeat. In that session the model asked for a failing one-liner twice more.
  * **Deny rules** win over everything, read-only commands included, and refuse without asking (`/permissions deny <rule>`); the model is told not to work around it.
  * **Plan mode and `/ask`** keep `run`, but only for commands that read; anything else is refused without a question (allowed or not).
  * **Storage:** each change is read-modify-write on the file, and rules are re-read when the file changes, so two sessions on one project share rules and neither loses the other's. A `"global"` section written by hand applies to every project.
  * **`/permissions`** lists allow and deny rules; `allow <rule>`, `deny <rule>`, `remove <rule>`, `clear`.
  * **Found in the audit and fixed:** a rule saved for `./scripts/x.sh` never matched again (and would have matched any `x.sh`); `git -C . push` slipped past the never-remember list and was offered a bare `git` rule; `cargo "test x"` matched the rule `cargo test`; `> 1` (a file named 1) was treated like `>&1`; `cat ~/.ssh/id_rsa` and `cat /etc/passwd` ran unasked; `uniq a b`, `tree -o`, `rg --pre`, `git grep -O`, `git reflog expire`, `hostname x`, `date -s` counted as read-only; `printenv` (it prints secrets) was on the read-only list; two sessions overwrote each other's rules; typing `a` where "always" wasn't on offer declined the command; plan mode couldn't run even `git log`. Found by the live run: saying "always" to `cargo --version` saved the rule `cargo`, which covered every cargo command.
  * **Differences from Claude Code that remain:** file edits are applied without asking (as in its accept-edits mode; `/undo` reverts the last turn's); there is no per-directory allow list for reading outside the project (it is asked each time unless a rule covers the command); rules are per project plus a hand-written global section, with no shared repository file.
  * **Tested:** the rules and every answer to the question are unit-tested; "Do you understand the current changes?" was run earlier on Qwen3.8-27B in `-p` mode (its git commands ran unasked; a correct summary in 42 s). A real terminal session on Qwen3.8-27B (driven through a pty): **a** to `cargo --version` saved a rule and the next `cargo --version` ran unasked; `rm -f …` was asked, answered with "do not delete anything; run `ls scripts` instead", and the model skipped the rm and ran `ls scripts`; `/permissions` listed the rule. A second session covered the rest: after `/permissions deny make`, `make --version` was refused without a question and the model said the deny rule forbade it; under `/ask`, `git log -1 --oneline` ran unasked and `cargo --version` was refused without a question; with a test MCP server, `notes.add_note` was asked once, **a** saved it, and the next call ran unasked (both notes were written). That session also showed `deny make` didn't cover `make --version` (a tool's name alone matched only the bare call, which is right for allow rules and wrong for deny rules); fixed, and re-run.
